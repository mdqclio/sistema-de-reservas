### 1b. Cobertura de `.validate`

`.validate` existe **exclusivamente** bajo `/cabanas/pendientes/$id` (6 campos + `datos/$campo`).

Nodos que aceptan **cualquier estructura, cualquier tipo y cualquier tamaño**, con la única condición de venir

`reservas` · `huespedes` · `movimientos` · `beds` · `precios` · `roles` · `usuarios` · `acl` ·
`categorias` · `proveedores` · `recurrentes` · `presupuestos` · `cierres` · `pipeline` · `auditoria` ·
`tipo_cambio_historial` · `knowledge_base` · `conversaciones` · `mensajes` · `emisores` · `facturas` ·
`checkin_tokens` · `bot_config` · `config_groq_key` · `_migrado` · `init` · `init_cabanas`

### 🟡 H-15 — Consecuencias concretas

- **Ningún tope de tamaño.** Nada impide que un huésped tenga un campo de 10 MB. De hecho ya pasa:
  el registro `h1776468570014` pesa 3.19 MB (ver H-05). Una regla `.validate` de longitud lo habría frenado.
- **Ninguna validación de tipo.** `movimientos/$id/monto` puede ser el string `"abolir"`; el cliente hace
  `Number(b.monto)` y todo el dashboard financiero pasa a `NaN`.
- **Ningún campo obligatorio.** Un `facturas/$id` sin `importe` o sin `emisorId` es válido para las reglas.
- **Ninguna inmutabilidad.** `auditoria/$id` es libremente editable y borrable por cualquier staff: el log
  de auditoría no es evidencia, es un scratchpad compartido.

### 1c. `.indexOn`

**No existe ningún `.indexOn` en ninguno de los dos archivos.** Verificado:

```
$ grep -rn "indexOn" security/   →  (sin resultados)
```

**Consultas que lo necesitarían:** ninguna hoy. `grep -n "orderByChild\|equalTo\|startAt\|endAt\|limitToFirst\|limitToLast\|orderByKey"`
sobre `index.html` devuelve **cero resultados**. El sistema no usa una sola query de RTDB: baja los nodos
completos y filtra en JavaScript (`getMovimientos().filter(...)`, `getReservas().find(...)`, etc.).

Eso significa que **la falta de `.indexOn` no es hoy el problema — es el síntoma**. El problema es el patrón
de "bajar todo y filtrar en el cliente", que a escala se paga en ancho de banda (sección 3).

### 1d. 🔴 H-02 — Granularidad de roles: las reglas no distinguen staff

Las reglas tienen **exactamente dos niveles de autorización**:

```jsonc
"cabanas": {
  ".read":  "auth != null && auth.provider !== 'anonymous'",
  ".write": "auth != null && auth.provider !== 'anonymous'"
}
```

Es decir: **anónimo** vs **no-anónimo**. El rol (`admin` / `recepcion` / `ventas` / `limpieza`) existe
únicamente en el cliente (`index.html:2672` `rolToKey()`, `2685` `applyRoleUI()`), y el cliente es
el atacante en cualquier modelo de amenaza serio.

Qué puede hacer un usuario con rol `limpieza` **a nivel reglas** (abriendo DevTools, o simplemente
`curl` con su ID token, sin tocar la UI):

| Acción | ¿La UI lo restringe? | ¿Las reglas lo restringen? | Severidad |
|---|---|---|---|
| Leer **todo** `/cabanas` (incl. DNI, teléfonos, emails, direcciones de 1.800 huéspedes) | Sí — `applyRoleUI()` oculta secciones | **No** | 🔴 |
| Escribir `/cabanas/usuarios/{su-id}` con `rol: 'rol-admin'` → **admin en el próximo login** | Sí — `.admin-only` oculta la sección Usuarios | **No** | 🔴 |
| Escribir `/cabanas/roles/rol-limpieza` con `permisos: {...todo 'rw'}` | Sí | **No** | 🔴 |
| Escribir `/cabanas/facturas/{k}` con `estado:'emitida'` y CAE inventado | Sí — `puedeSolicitarFactura()` L2716 | **No** | 🔴 |
| Escribir `/cabanas/emisores/{k}` con un CUIT ajeno | Sí | **No** | 🟠 |
| Reescribir `/cabanas/precios` entero (tarifas de las 12 cabañas) | Sí — módulo `precios` por rol | **No** | 🟠 |
| Borrar `/cabanas/reservas` completo | Sí | **No** | 🟠 |
| Editar o borrar entradas de `/cabanas/auditoria` (borrar su propio rastro) | Sí | **No** | 🟠 |
| Leer `/cabanas/config_groq_key` (API key de Groq) | Sí | **No** | 🟠 |
| Leer/escribir `/cabanas/conversaciones` y `/cabanas/mensajes` | Sí | **No** | 🟡 |

**Todas las filas son "la UI restringe pero las reglas no".** El control de acceso del sistema es
enteramente cosmético: son `element.style.display = 'none'` (líneas 2689-2699).

### 🔴 H-01 — Suplantación / escalada a admin (punto 2 del brief)

Es el caso más grave de H-02 porque cierra el círculo. `enterSession()` (L2624-2662) resuelve el rol así:

```js
// index.html:2631-2640
const usuarios = colUsuarios.list();                                  // ← /cabanas/usuarios
const u = usuarios.find(x => x.email && x.email.toLowerCase()===email.toLowerCase());
if(!u) { await signOut(auth); ... }
const rol = roles.find(r=>r.id===u.rol);                              // ← /cabanas/roles
const rolKey = rolToKey(u.rol);
currentUser = { id: u.id, name: u.nombre, email: u.email, rol: u.rol, rolKey };
```

`/cabanas/usuarios` es **escribible por cualquier usuario no anónimo** (regla del padre `/cabanas`).
No hay ninguna cláusula que ate `usuarios/$id` al `auth.uid` del que escribe, ni que haga
`rol` inmutable, ni que exija que quien cambia un rol sea admin.

**Cadena de ataque completa (3 pasos, ~30 segundos):**

1. Usuario `limpieza@…` inicia sesión normalmente en la app (credenciales legítimas).
2. Desde DevTools:
   ```js
   // su propia fila, con el rol cambiado
   await set(ref(db,'cabanas/usuarios/u1774658979321'),
             {...miFila, rol:'rol-admin', estado:'activo'});
   ```
3. Recarga la página. `enterSession()` relee `/cabanas/usuarios`, encuentra `rol: 'rol-admin'`,
   `rolToKey()` devuelve `'admin'`, `applyRoleUI()` desbloquea todo. **Admin persistente.**

Ni siquiera hace falta el paso 1 con una cuenta de staff: cualquiera que consiga **crear** un usuario en
Firebase Auth (el proveedor Email/Password está habilitado y `createUserWithEmailAndPassword` está importado
en L1783) puede insertar su propia fila en `/cabanas/usuarios` con `rol: 'rol-admin'` y entrar como admin
sin que nadie lo dé de alta. El único freno es si el registro público de Auth está deshabilitado en la
consola — **no verificable desde el repo** (ver "Qué no se pudo verificar").

**Uso del uid de Firebase Auth:** el `uid` se usa en **un solo lugar**, `index.html:2646`:

```js
await set(ref(db, 'cabanas/acl/' + auth.currentUser.uid), { rol: u.rol, rolKey, email: u.email });
```

y ese valor **se deriva de `u.rol`**, o sea del mismo nodo `usuarios` que el atacante acaba de falsificar.
Todo lo demás —identidad, rol, permisos, `auditLog` (`usuario: currentUser?.name`, L4781)— cuelga del
**email**, que no está criptográficamente atado a nada del lado servidor.

### 🟡 H-17 — `/cabanas/acl` es infraestructura muerta

`acl` se escribe en cada login (L2646) y su comentario dice *"para que las reglas RTDB por rol (Tier 2)
puedan leerlo"*. Pero **ninguna regla de ninguno de los dos archivos referencia `acl`**. Verificado: el
único bloque `acl` en las reglas es el `.write` de `$uid`, que no lee nada.

Resultado: `acl` es un nodo write-only que consume escrituras en cada login y transmite una falsa sensación
de que existe un tier de autorización por rol. No lo hay. (El template `database.rules.per-rol.template.json`
existe en `security/` pero nunca se desplegó.)

### 1e. `checkin_tokens`

```jsonc
"checkin_tokens": {
  ".write": "auth != null && auth.provider !== 'anonymous'",   // solo staff
  "$token": { ".read": "auth != null" }                        // cualquiera con sesión, incl. anónima
}
```

**Anti-listado: ✅ correcto.** El padre `checkin_tokens` **no tiene `.read`**. En RTDB las reglas hijas solo
pueden *ampliar* acceso, nunca restringir, así que el `.read` a nivel `$token` no se propaga hacia arriba: un
anónimo que hace `GET /cabanas/checkin_tokens.json` recibe *Permission denied*, y no puede enumerar tokens.
El `.read` de `/cabanas` sí cubre el padre, pero exige no-anónimo. Correcto y bien comentado.

**Qué puede hacer un anónimo que conoce un token** (`docs/checkin.html:46`):

| Puede | No puede |
|---|---|
| Leer `checkin_tokens/{token}` → `{reservaId, hab, entrada, salida, ...}` (L7898-7899) | Escribir o borrar el token (`.write` es solo staff, y `$token` no lo amplía) |
| Crear un `/cabanas/pendientes/{k}` con `tipo:'precheckin'` y ese token | Leer `/cabanas/reservas` u otro nodo |
| Repetir la creación indefinidamente con el mismo token (ver H-07) | Listar tokens |

El token es opaco y no adivinable (`crypto.randomUUID()`, L7895) ✅. **Punto débil:** el token no expira ni
tiene TTL en el dato; solo se consume cuando el staff hace check-in (`confirmCheckin()` L3814) o promueve el
pendiente (L7845). Una reserva a la que nunca se le hace check-in deja el token vivo para siempre, y
`reservaId`+`hab`+fechas quedan legibles por quien tenga el link (que viajó por WhatsApp).

### 1f. 🟠 H-07 — El carve-out create-only de `pendientes`

```jsonc
"$id": {
  ".write": "(auth != null && !data.exists() && newData.exists()) || (auth != null && auth.provider !== 'anonymous')"
}
```

| Vector | ¿Resiste? | Por qué |
|---|---|---|
| **Sobreescritura** de un pendiente ajeno por un anónimo | ✅ Sí | `!data.exists()` falla si el nodo ya existe, y la segunda cláusula exige no-anónimo. |
| **Borrado** por un anónimo | ✅ Sí | `newData.exists()` falla en un delete (`newData` es null). |
| **Adivinar la key de otro pendiente** | ✅ Sí | Son push keys de 20 caracteres. Y aunque la adivine, no puede leerla ni pisarla. |
| **Spam de creación masiva** | ❌ **No** | Sin límite alguno. |

**El vector de spam, en detalle.** `docs/guest-register.html` **no requiere token**: cualquiera con la URL
(que es pública y está en `docs/`, servida por GitHub Pages) puede:

```js
// guest-register.html:32, 104-105
await signInAnonymously(auth);
const key = push(ref(db, 'cabanas/pendientes')).key;
await set(ref(db, 'cabanas/pendientes/' + key), rec);   // rec.fotoDni hasta 500 KB
```

`apiKey` y `databaseURL` están en el HTML (líneas 17-18), que es lo normal en Firebase, pero significa que un
script de 10 líneas replica el flujo sin abrir el navegador.

**Nada limita el volumen:**
- Sin App Check.
- Sin rate limit por regla (RTDB no tiene ninguno nativo; el patrón habitual es un nodo `throttle/$uid`
  con `newData.child('ts').val() > data.child('ts').val() + 60000`, que acá no existe).
- Sin límite de cantidad de hijos de `pendientes`.
- El anónimo puede pedir un `uid` nuevo por cada request (`signInAnonymously` sin persistencia), así que ni
  siquiera un throttle por uid alcanzaría sin App Check.

**Costo del ataque:** 500 KB por registro × N. Un script casero a 10 req/s sube **~18 GB por hora** a la
base. En Blaze eso es storage a $5/GB-mes + el download de cada cliente que tenga la app abierta, porque
`attachPendientesLive()` (L7717) escucha `/cabanas/pendientes` **completo** y `updatePendientesBadge()` cuenta
los hijos. Los 3 navegadores de staff se comen la inyección en vivo. En Spark, la base se corta sola al
llegar al límite y **el sistema entero deja de funcionar** (la app no arranca sin `loadAllData()`).

El `.validate` de `fotoDni < 500000` acota el registro individual, no el total. Es un tope por bala, no por
cargador.

### 1g. 🟠 H-06 — Facturación: las reglas no distinguen a n8n del staff

Las reglas de `facturas` (solo en staging, y **todavía sin publicar** según `"//pendiente"`):

```jsonc
"facturas": {
  ".read":  "auth != null && auth.provider !== 'anonymous'",
  ".write": "auth != null && auth.provider !== 'anonymous'"
}
```

El comentario dice *"El procesador externo (n8n) escribe con credencial de servicio, no anónima"* — cierto,
pero **la regla no puede distinguir esa credencial de la de un recepcionista**. Ambas son `auth != null` y
no anónimas. No hay `auth.token.admin`, ni un uid de servicio en la condición, ni una separación de
subárboles (staff escribe la solicitud, n8n escribe el resultado).

**Vector completo:**

1. Staff crea la solicitud legítima: `crearSolicitudFactura()` (L5561-5633) escribe
   `estado: 'pendiente'`, `cae: ''`, `nroComprobante: ''`, y `movimientoIds: [...]`.
2. En vez de esperar a n8n, el mismo staff (o cualquiera, incluido `limpieza`) escribe desde DevTools:
   ```js
   await set(ref(db,'cabanas/facturas/-OxAbC123'),
     {...reg, estado:'emitida', cae:'71234567890123', nroComprobante:'99', vencimientoCae:'20261231'});
   ```
3. El listener de facturas dispara en **todos los clientes conectados** (L5323-5328) y llama a
   `conciliarFacturasEmitidas()` (L5353-5368), que hace:
   ```js
   const nro = nroComprobanteFmt(f);                                  // "0005-00000099"
   await writeMovimiento({ ...m, facturado: true, nroComprobante: nro });
   ```
4. Los movimientos quedan `facturado: true` con un comprobante que **no existe en ARCA**.

**Consecuencias:** esos movimientos desaparecen de `movimientosFacturables()` (filtra `!m.facturado`), o sea
**nunca se facturan de verdad**; el dashboard reporta `facturadoARS` e `IVA (21% s/ facturado)` (L4816-4818)
sobre ventas no declaradas; y el CAE falso queda en el registro contable. Es diferencia entre lo declarado y
lo cobrado, con rastro en la base.

Agravante: no hay ningún campo que ate la escritura a su autor. `creadoPor` (L5616) lo pone el propio cliente
y es libremente falsificable. `auditLog('solicitar factura', ...)` (L5626) también corre en el cliente y
se puede saltear escribiendo directo a la base.

**Corrección importante sobre el costo por escritura.** El brief asume que *"cada escritura de cualquier
usuario re-baja ese nodo completo en todos los clientes conectados"*. Eso **no es exacto para RTDB**, y la
diferencia cambia la proyección por dos órdenes de magnitud, así que conviene fijarlo:

- RTDB mantiene una conexión WebSocket persistente y, ante el cambio de un hijo, envía **solo el delta de ese
  hijo**, no el nodo entero. El costo de red de un `writeReserva()` de 388 B es ~388 B × 3 clientes.
- Lo que **sí** baja el nodo completo es el **attach inicial** del listener — una vez por carga de página.
- Lo que **sí** re-envía el nodo entero por escritura es un `set()` de nodo entero: `DB.set('precios', p)`
  (L1810-1817) reescribe `/cabanas/precios` completo, así que los 3 clientes reciben los 2.6 KB enteros. Con
  26 call-sites (ver H-12), editar un precio cuesta el nodo entero en cada cliente. Ídem `bot_config`.
- Lo que sí es caro por escritura del lado **cliente** es el callback: `{ ...remote }` clona el nodo completo
  en memoria (L1883, L2363) y llama al re-render, que reconstruye tablas de miles de filas con `innerHTML`.
  A 12.000 movimientos eso es un freeze visible de UI, no un costo de facturación.

La conclusión práctica no cambia: **el gasto dominante es el attach inicial × frecuencia de carga de página**,
y ahí el problema es el tamaño del árbol.

restantes reaparecen en `movimientosFacturables()` y se pueden facturar de nuevo (esto es H-08).

### 🟡 H-16 — `conciliarFacturasEmitidas` corre en los 3 clientes

Se dispara desde el listener de `facturas` (L5327), o sea **en cada cliente conectado, simultáneamente**,
sobre el mismo conjunto de movimientos. El guard de idempotencia:

```js
// index.html:5364
if (m.facturado === true && (m.nroComprobante || '') === nro) continue;
```

lee `cache.movimientos[id]`, que es el **cache local**. Los 3 clientes leen su cache pre-actualización a la
vez, ninguno ve el `facturado:true` del otro, y los 3 escriben el mismo `writeMovimiento()`. El resultado
final es idempotente (mismo valor), así que no corrompe datos — pero triplica las escrituras y, en un nodo de
12.000 movimientos con facturas de 15 ítems, son 45 escrituras donde debía haber 15.

#### 🟡 Cierre de caja (`cerrarCaja`, L5732-5757) — 1 escritura

Una sola: `colCierres.write({...})` (L5741) ✅. Sin problema de atomicidad.

Dos observaciones aparte: (a) no hay `await` en L5741 ni en el `auditLog` que sigue, así que el `showNotif`
de éxito aparece antes de saber si la escritura funcionó; (b) nada impide cerrar dos veces el mismo día
—no hay chequeo de cierre existente para `fecha === today()`—, y cada cierre recalcula sobre los mismos
movimientos.

#### 🟠 `aplicarRecurrentes` (L5052-5080) — 2 escrituras por recurrente, en loop

| Paso | Línea | Escritura |
|---|---|---|
| 1 | 5060 | `writeMovimiento({...})` — el egreso recurrente |
| 2 | 5073 | `colRecurrentes.write(r)` con `r.ultimaAplicacion = hoy` |

Si muere entre 1 y 2: **el egreso quedó registrado pero el recurrente no quedó marcado como aplicado**. Al
próximo login (o al de otro usuario, ver abajo) se vuelve a aplicar → **egreso duplicado en la caja**.

Agravante de concurrencia: `aplicarRecurrentes()` se llama desde `enterSession()` (L2656), o sea **en cada
login de cada usuario**. Si dos personas entran a la vez a la mañana, ambos ven `ultimaAplicacion !== hoy` y
**ambos escriben el egreso**. El guard es un read-then-write sin transacción. Con 3 staff que entran cada
mañana, el gasto recurrente del día 5 de cada mes se registra hasta 3 veces.

## 6. XSS — inventario de sinks

**`escapeHtml()` es correcto** (L6977-6982): escapa los 5 caracteres (`& < > " '`), coerciona `null`/`undefined`
a `''`, y es seguro también dentro de atributos.

Cobertura: 91 usos de `innerHTML` contra 121 llamadas a `escapeHtml`. El escapado es la norma. Los sinks que
se escapan de la norma:

### 🟠 H-09 — `renderKnowledge()` (L7484-7501): 5 campos sin escapar

```js

  ? `<div style="...">${item.category||'General'}</div>
     <div style="...">${item.question}</div>

  : `<div style="...">${item.texto}${origen==='corrección'?...}</div>`;
```

```js
// index.html:7500 — dentro de un <textarea>
<textarea class="kb-text-edit" id="kb-edit-${id}" style="...">${textoEdit}</textarea>
```

y `facMovsSeleccionados()` (L5380-5382) repite el mismo criterio: `!m.facturado`.

El campo `facturado` **solo se pone en `true`** en `conciliarFacturasEmitidas()` (L5365), que se ejecuta
únicamente cuando la factura llega a `estado === 'emitida'` (L5356). Entre que el staff aprieta "Facturar" y
que n8n devuelve el CAE, la factura está en `'pendiente'` y después `'procesando'` — y durante toda esa
ventana **los movimientos siguen con `facturado === false`, o sea siguen apareciendo en la lista y se pueden
volver a tildar**.

**Reproducción:**
1. Tildar el movimiento `M`, apretar 🧾 Facturar. Se crea `facturas/-A` con `estado:'pendiente'`,
   `movimientoIds:['M']`. `facSeleccion.clear()` (L5627) limpia la selección y `renderAcct('facturacion')`
   redibuja.
2. `movimientosFacturables()` corre de nuevo: `M` sigue con `facturado === false` ⇒ **vuelve a aparecer en la
   lista**.
3. Tildar `M` otra vez, Facturar. Se crea `facturas/-B` con el mismo `movimientoIds:['M']`.
4. n8n procesa ambas. **Dos facturas en ARCA por el mismo cobro.**

Agravantes:
- La ventana no es corta: depende del ciclo de n8n contra ARCA (segundos a minutos, más si ARCA está caído o
  si n8n está parado — y entonces la factura queda en `'pendiente'` indefinidamente).
- Con 2-3 recepcionistas mirando la misma lista, los dos ven `M` disponible al mismo tiempo. No hace falta
  que sea la misma persona.
- Nada en la UI indica que `M` ya tiene una solicitud en vuelo.
- Una factura en `'error'` **sí** debe volver a la lista (es reintentable), así que no alcanza con excluir
  todo lo referenciado.

Excluir los `movimientoIds` referenciados por facturas que no estén en `'error'`:

```js
// Las facturas en 'error' NO cuentan: son reintentables y sus movimientos deben volver a la lista.
function movimientoIdsComprometidos() {
  const s = new Set();
  for (const [, f] of facturasEntries()) {
    if (f.estado === FACTURA_ESTADOS.ERROR) continue;
    (Array.isArray(f.movimientoIds) ? f.movimientoIds : []).forEach(id => s.add(id));
  }
  return s;
}

function movimientosFacturables() {
  const comprometidos = movimientoIdsComprometidos();
  return getMovimientos()
    .filter(m => m && m.tipo === 'ingreso' && !m.facturado && (m.moneda || 'ARS') === 'ARS')
    .filter(m => !comprometidos.has(m.id))                    // ← nuevo
    .filter(m => !facFiltro.desde || (m.fecha || '') >= facFiltro.desde)
    .filter(m => !facFiltro.hasta || (m.fecha || '') <= facFiltro.hasta)
    .sort((a, b) => String(b.fecha || '').localeCompare(String(a.fecha || '')));
}

// Mismo criterio en el punto de confirmación, para cerrar la carrera entre dos
// recepcionistas que tildaron el mismo movimiento antes de que llegara el eco del listener.
function facMovsSeleccionados() {
  const comprometidos = movimientoIdsComprometidos();
  return getMovimientos().filter(m =>
    m && facSeleccion.has(m.id) && m.tipo === 'ingreso' && !m.facturado && !comprometidos.has(m.id));
}
```

Complemento recomendado en la UI: mostrar los movimientos comprometidos en la tabla, deshabilitados y con un
badge del estado de su factura, en vez de esconderlos — así el recepcionista entiende por qué no puede

### R-15 · Migrar a queries + `.indexOn` (secciones 1c y 3)

El techo real del diseño es "bajar todo y filtrar en JS". A 12.000 movimientos, `renderCaja()` baja el nodo
entero para mostrar los ~13 del día. La migración natural, por orden de retorno:

1. `movimientos` → `orderByChild('fecha').startAt(desde).endAt(hasta)` + `.indexOn: ["fecha"]`.
   Es el nodo que más crece y el que se filtra por fecha en 4 lugares.
2. `reservas` → `orderByChild('salida').startAt(hoy)` + `.indexOn: ["entrada","salida","estado"]`.
   La grilla y el mapa solo necesitan la ventana visible.
3. `auditoria` → `orderByChild('ts').limitToLast(100)` + `.indexOn: ["ts"]`. `renderAuditoria()` ya muestra
   solo 100 (L5087) — hoy baja las 1.000 para descartar 900.

Con eso, `loadAllData()` deja de existir como "un GET de todo" y pasa a ser un puñado de queries acotadas.

### R-16 · `.validate` de tipo y tamaño en todo el árbol (H-15)
